# Working conventions

## Writing style

No em dashes in new or edited text: not in prose, docs, commit messages, or
code comments. Use colons, commas, parentheses, or full stops instead.

This applies going forward, not as a retroactive sweep. RESULTS.md and
README.md predate the convention; rewriting them risks mangling sentences
where the dash joins two clauses. Leave existing em dashes in those files
alone unless you're already editing the sentence they're in.

## Data integrity

- Never write a number into RESULTS.md that isn't backed by a committed
  file. If the raw data isn't in the repo, say so and stop. Don't
  transcribe it from conversation.
- Never edit or regenerate raw JSON under `results/device-pull/`. It's the
  record of what was actually measured. Corrections go in RESULTS.md as
  annotations, not edits to the raw files.
- When a later session overturns an earlier finding, add a
  forward-pointing correction to the earlier session's entry. Never
  silently rewrite it: the revision history is part of what makes the
  document trustworthy.
- Every figure in RESULTS.md states the conditions that produced it, and
  flags anything estimated rather than calculated.

## Outward-facing claims

This applies to anything that leaves the repo: CFP abstracts, talk slides,
README text, articles, posts.

- Every claim must be something we measured ourselves, on hardware we ran.
  Not inferred, not assumed, not carried over from documentation or from
  what is generally known to be true. If we did not test it, it does not go
  in, however safe it sounds.
- "Generally true" is not a pass. Documented platform behaviour may be said
  on stage as platform behaviour, but it is never presented as one of our
  findings, and it never sits inside a sentence that reads as a result.
- Check claims against the raw files, not against RESULTS.md prose. Prose
  is where the earlier mistakes lived. If a figure cannot be traced to a
  committed JSON or a committed screenshot, say so and cut it.
- Count and compute rather than eyeball. Word counts, sample counts,
  percentages, ranges: run them. An estimate written as a figure is a
  fabrication, including in audit notes about fabrications.
- A claim about the field ("nobody has published", "every benchmark does
  X") requires a survey we actually did. We have not done one, so these do
  not go in.
- Single-device results are phrased as observations in past tense, and the
  fact that they are one device is stated wherever the number appears.
- State the range, not the flattering end of it. Round in the direction
  that understates our case.
- When a claim is cut for being unprovable, record what it was and why in
  the file it was cut from. The list of removed claims is part of the
  evidence that the remaining ones were checked.

## Charts

- Charts are generated by scripts in `analysis/`, never dropped in from
  elsewhere. A figure nothing reproduces doesn't belong in the repo.
- Before adding files to an existing chart's input set, check whether
  that chart is already embedded somewhere with a specific meaning.

## General

- When text is marked as going somewhere verbatim, reproduce it exactly.
  Don't reword or tighten it.
- Flag gaps rather than filling them. Refusing to write something
  unsupported is the correct behaviour here.
